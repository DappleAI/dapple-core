# dapple-data

Data access layer for Dapple Prompt, providing type-safe PostgreSQL operations with SQLx.

## Overview

The `dapple-data` crate implements a high-performance data layer designed around batch operations, append-only semantics, and compile-time SQL verification. It serves as the single source of truth for all database interactions across the Dapple ecosystem.

**Note:** Public DTO types (consumer-facing structs like `Guide`, `Journey`, `Category`, etc.) now live in `dapple-types` and are re-exported here. See [`dapple-types/README.md`](../dapple-types/README.md) for the full type inventory. This crate retains all internal models, query functions, SQL assets, and `From<Model> for DTO` conversions.

## Core Principles

### 1. Append-Only Architecture
- Default to INSERT operations over UPDATE
- Track state changes via new records
- Enable complete audit trails and time-travel queries

### 2. Set-Wise Operations
All operations use column-wise parameters with `UNNEST WITH ORDINALITY`:

```sql
WITH args AS (
    SELECT *
    FROM UNNEST(
        $1::TEXT[],    -- names
        $2::BIGINT[]   -- parent_ids
    ) WITH ORDINALITY AS o(name, parent_id, ord)
)
```

### 3. Ordering Guarantees
Results preserve input order using the `ord` column from `UNNEST`:

```sql
ORDER BY args.ord
```

### 4. Type Safety
All SQL queries use `sqlx::query_file_as!` macro for compile-time verification against generated `.sql` files:

```rust
let rows = sqlx::query_file_as!(
    InsertedJourneyModel,
    "assets/.sql/journeys/insert_journeys.sql",  // generated by sql-composer
    &names,
    &parent_ids
)
.fetch_all(pool)
.await?;
```

### 5. sql-composer Pipeline
SQL sources are authored as `.sqlc` files in `assets/sqlc/` using `:compose()` and `:bind()` directives, then compiled to `.sql` output in `assets/.sql/` via `cargo sqlc compose`. See [AGENTS.md](./AGENTS.md#sql-composer-workflow) for the full workflow.

## Object Model

### Principal Objects
Top-level entities with independent lifecycles:
- **Playbook** — Collection of journeys with versioning
- **Journey** — Ordered sequence of steps
- **Step** — Individual task execution unit
- **Task** — Reusable task definition
- **Dispatch** — Workflow execution instance
- **Brief** — Versioned brief content (no dependencies)
- **BriefGroup** — Versioned group referencing Briefs via associative table
- **BriefPack** — Versioned pack referencing BriefGroups via associative table
- **Guide** — Versioned structured documentation (chapters, blocks, tags) with audience targeting

Each principal has:
- Dedicated database table
- `object_id` (UUID) for external references
- Optional versioning with `path_id`

### Owned Dependents
Data owned by a principal with same lifecycle:
- Created/deleted with parent
- Foreign key to parent table
- Included in parent's query results

Example: `journey_steps` (join table between journeys and steps)

### Shared Dependents
Data shared across multiple principals:
- Independent lifecycle
- Referenced by `object_id`
- Must exist before being referenced

Example: A `Task` can be used in multiple `Steps`

### Versioned Objects
- Immutable versions tracked via path:
- `path_id` → references Path Object
- `version_major`, `version_minor`, `version_patch`
- PATCH creates new version, doesn't modify existing

Example: `playbooks` table with `playbook_paths`

## Key Concepts (for agents & tests)
A concise glossary of terms and conventions relied on by automated agents, lifecycle tests, and contributors.

- Principal Object
  - Top-level domain entity created independently (e.g., Playbook, Journey, Step).
  - Has its own table and lifecycle; owned dependents are created with it.
  - Typical files: `crates/dapple-data/assets/sqlc/<principal>/` (sources), `crates/dapple-data/assets/.sql/<principal>/` (generated), `crates/dapple-data/src/query/<principal>.rs`.

- Owned Dependent
  - Object that is created and managed by a Principal's POST (no separate pre-seeding).
  - Stored in a table with an FK to the principal; included in parent's SELECT results.
  - Example: journey steps that live with a Journey.

- Shared Dependent
  - Reusable object with an independent lifecycle that must exist before being referenced (e.g., Task).
  - Created separately and referenced by `object_id` in principals/children.
  - Tests must seed shared dependents before creating principals that reference them.

- ScenarioContext & BatchHandle (testing)
  - `ScenarioContext`: shared test state used by lifecycle tests to store named batches of created objects.
  - `BatchHandle`: lightweight handle (name + vector of objects) stored in `ScenarioContext` so later tests can poll/wait for dependencies.
  - See `crates/dapple-prompt-api/tests/` for usage patterns.

- CreateXSchema
  - Client-side POST payload naming convention used by tests and handlers (e.g., `CreateJourneySchema`).
  - Tests log and assert on these payloads when diagnosing failures.

- InsertXArgs
  - Column-wise insert arguments: flattened vectors passed into SQL via UNNEST (each vector must have identical length).
  - Example type: `InsertJourneyArgs { names: Vec<String>, playbook_ids: Vec<i64> }`.
  - SQL assets use a single UNNEST(... ) WITH ORDINALITY and join `args.ord` to preserve ordering.

- FlatXModel / InsertedXModel / PublicXModel (naming)
  - `FlatXModel`: a flattened SQL JOIN row (used as the intermediate from `query_file_as!`).
  - `InsertedXModel`: the INSERT...RETURNING row type.
  - Public DTO (e.g., `Category`, `Guide`): API-facing DTO returned by handlers, defined in `dapple-types` and re-exported here. Uses `id: Uuid` (UUIDv7) as the primary identifier.
  - Follow exact names (`FlatXModel`, `InsertedXModel`, `InsertXArgs`, `CreateXSchema`) — tests and code rely on these identifiers.

## Model & Naming (quick mapping)
- Define Rust model types under `crates/dapple-data/src/model/`.
- Put query functions under `crates/dapple-data/src/query/` and SQL sources under `crates/dapple-data/assets/sqlc/`. Run `cargo sqlc compose` to generate `assets/.sql/`.
- Keep `object_id: Uuid` on public DTOs and internal `id: i64` on DB-facing models.

## Testing & Lifecycle Patterns
Guidance for writing reliable lifecycle/integration tests that exercise the same flow as the API handlers.

- Batch naming
  - First batch for an endpoint should follow the pattern: `"{endpoint}-init"` (e.g., `journeys-init`).
  - Store batches in `ScenarioContext` so dependent tests can wait for them.

- Ordering & Inserts
  - Preserve ordering for multi-row inserts by building `InsertXArgs` where every vector has identical length and using a single `UNNEST(... ) WITH ORDINALITY` in SQL.
  - Use `ORDER BY args.ord` in the final SELECT so the returned rows match input order.

- Waiting for shared dependents
  - Tests must explicitly poll `ScenarioContext` for the required `BatchHandle` instead of sleeping.
  - This makes tests deterministic and avoids flaky timing issues.

- Validation between POST and GET
  - Compare POST (INSERT...RETURNING) responses against GET results to ensure queries return the same projected fields and ordering.
  - Use the same SQL assets for both INSERT and SELECT where possible to reduce drift.

## SQL & Query Patterns (notes / quick rules)
- Always prefer `.sqlc` sources under `crates/dapple-data/assets/sqlc/` over inlined SQL strings in Rust. Never edit `assets/.sql/` directly — it is generated by `cargo sqlc compose`.
- When adding multi-row inserts, build `InsertXArgs` and use a single UNNEST call with WITH ORDINALITY. This preserves input ordinals and enables deterministic ordering.

Short UNNEST-with-ORDINALITY pattern (reference):

WITH args AS (
    SELECT *
    FROM UNNEST($1::BIGINT[], $2::TEXT[]) WITH ORDINALITY AS o(col1, col2, ord)
)
... final INSERT/SELECT ...
ORDER BY args.ord;

- Add a corresponding function under `crates/dapple-data/src/query/<area>.rs` that calls `sqlx::query_file_as!` pointing at the generated `assets/.sql/` path. Pass parameters in **alphabetical order** of `:bind()` names.
- When editing `.sqlc` sources, prefer `dapple sqlc compose` (compose + prepare in one); the raw equivalent is `cargo sqlc compose` then `cargo sqlx prepare --workspace -- --all-targets`, after which you commit `.sqlx/` (see SQLx & CI).

## Migrations, IDs, and Indexing (short reminders)
- Put schema migrations in `crates/dapple-data/migrations/` and follow `ddl.instructions.md` when changing types/constraints.
- Primary keys: prefer `BIGINT GENERATED ALWAYS AS IDENTITY` for internal numeric IDs; use `UUID` only when externally required.
- JSONB: use `jsonb` for flexible attributes and add GIN indexes; use generated columns + B-tree indexes for frequently queried scalar fields.
- Indexes: add explicit FK indexes — Postgres does not auto-index foreign keys.

## SQLx & CI
- For offline SQL verification in CI/Docker builds set `SQLX_OFFLINE=true` and commit the generated `.sqlx/` metadata after running:

```bash
# Preferred: `dapple sqlx prepare` (wraps the command below).
cargo sqlx prepare --workspace -- --all-targets
```

- Keep `.sqlx/` up-to-date when changing SQL assets so `sqlx::query_file_as!` continues to verify at compile-time.

## Diagnostics & Debugging (failing tests checklist)
When lifecycle/integration tests fail, log these items to help root-cause the issue:

1. The `CreateXSchema` payload(s) that were POSTed.
2. The lengths of each vector in the constructed `InsertXArgs` (mismatched lengths are a common failure).
3. The exact rows returned by the failing SQL (INSERT...RETURNING or SELECT) and the SQL asset path used.

Helpful places to inspect: `crates/dapple-data/assets/sqlc/` (sources), `crates/dapple-data/assets/.sql/` (generated), `crates/dapple-data/src/query/`, `crates/dapple-prompt-api/tests/`.

## SQL Query Patterns

### INSERT Pattern
```sql
-- Source: assets/sqlc/journeys/insert_journeys.sqlc
-- Generated: assets/.sql/journeys/insert_journeys.sql
WITH args AS (
    SELECT *
    FROM UNNEST($1::TEXT[], $2::BIGINT[])
    WITH ORDINALITY AS o(name, playbook_id, ord)
),
objs AS (
    INSERT INTO web.journeys (object_id, name, playbook_id, created_at)
    SELECT gen_random_uuid(), args.name, args.playbook_id, now()
    FROM args
    RETURNING *
)
SELECT
    objs.id,
    objs.object_id,
    objs.name,
    p.object_id as playbook_object_id,
    objs.created_at,
    (SELECT ord FROM args WHERE args.playbook_id = objs.playbook_id) as ord
FROM objs
JOIN web.playbooks p ON p.id = objs.playbook_id
ORDER BY ord;
```

### SELECT Pattern
```sql
-- Source: assets/sqlc/journeys/select_journeys_by_object_ids.sqlc
WITH args AS (
    SELECT *
    FROM UNNEST($1::UUID[]) WITH ORDINALITY AS o(object_id, ord)
)
SELECT
    j.id,
    j.object_id,
    j.name,
    s.id as step_id,
    s.object_id as step_object_id,
    s.name as step_name,
    t.object_id as task_object_id,
    args.ord
FROM args
JOIN web.journeys j ON j.object_id = args.object_id
LEFT JOIN web.journey_steps js ON js.journey_id = j.id
LEFT JOIN web.steps s ON s.id = js.step_id
LEFT JOIN web.tasks t ON t.id = s.task_id
ORDER BY args.ord, s.id;
```

### PATCH Pattern (Versioned Objects)
```sql
-- Source: assets/sqlc/playbooks/patch_playbooks.sqlc
WITH args AS (
    SELECT *
    FROM UNNEST($1::UUID[], $2::TEXT[])
    WITH ORDINALITY AS o(object_id, name, ord)
),
paths AS (
    SELECT
        pp.id as path_id,
        COALESCE(MAX(p.version_patch), 0) as latest_patch,
        args.ord
    FROM args
    JOIN web.playbook_paths pp ON pp.object_id = args.object_id
    LEFT JOIN web.playbooks p ON p.path_id = pp.id
    GROUP BY pp.id, args.ord
),
objs AS (
    INSERT INTO web.playbooks (path_id, name, version_patch, created_at)
    SELECT paths.path_id, args.name, paths.latest_patch + 1, now()
    FROM args
    JOIN paths ON paths.ord = args.ord
    RETURNING *
)
SELECT * FROM objs ORDER BY ord;
```

```rust
/// Insert batch of journeys
pub async fn insert_journeys(
    pool: &PgPool,
    args: InsertJourneyArgs,
) -> Result<Vec<InsertedJourneyModel>, DataError> {
    // Validate vectors are same length
    assert_eq!(args.names.len(), args.playbook_ids.len());

        InsertedJourneyModel,
        "assets/.sql/journeys/insert_journeys.sql",
        // Parameters in alphabetical order of :bind() names
        &args.names,
        &args.playbook_ids
    )
    .fetch_all(pool)
    .await?;

    Ok(rows)
}
```

### Select Function
```rust
/// Select journeys by object IDs
pub async fn select_journeys_by_object_ids(
    pool: &PgPool,
    object_ids: &[Uuid],
) -> Result<Vec<JourneyModel>, DataError> {
    let flat_rows = sqlx::query_file_as!(
        FlatJourneyModel,
        "assets/.sql/journeys/select_journeys_by_object_ids.sql",
        object_ids
    )
    .fetch_all(pool)
    .await?;

    // Fold flat rows into structured models
    let models = fold_journeys(flat_rows)?;
    Ok(models)
}

/// Convert flat JOIN results into structured models
fn fold_journeys(
    flat: Vec<FlatJourneyModel>
) -> Result<Vec<JourneyModel>, DataError> {
    use itertools::Itertools;

    let grouped = flat.into_iter()
        .group_by(|row| row.id);

    let models = grouped.into_iter()
        .map(|(journey_id, rows)| {
            let rows: Vec<_> = rows.collect();
            let first = &rows[0];

            let steps = rows.into_iter()
                .filter_map(|row| {
                    row.step_id.map(|step_id| StepModel {
                        id: step_id,
                        object_id: row.step_object_id.unwrap(),
                        name: row.step_name.unwrap(),
                        task_object_id: row.task_object_id,
                    })
                })
                .collect();

            Ok(JourneyModel {
                id: first.id,
                object_id: first.object_id,
                name: first.name.clone(),
                playbook_id: first.playbook_id,
                playbook_object_id: first.playbook_object_id,
                steps,
            })
        })
        .collect::<Result<Vec<_>, DataError>>()?;

    Ok(models)
}
```

## Database Schema Guidelines

### Table Design
```sql
CREATE TABLE web.journeys (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    object_id UUID NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    name TEXT NOT NULL,
    playbook_id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT fk_playbook
        FOREIGN KEY (playbook_id)
        REFERENCES web.playbooks(id)
);

-- Explicit index on FK (PostgreSQL doesn't auto-create)
CREATE INDEX idx_journeys_playbook_id ON web.journeys(playbook_id);
```

### Naming Conventions
- Tables: plural snake_case (`journeys`, `playbook_steps`)
- Primary key: `id` (BIGINT)
- Foreign keys: `{table_singular}_id`
- Timestamps: `{adjective}_at` (e.g., `created_at`)
- Constraints: `fk_{reference}`, `uk_{column}`, `chk_{constraint}`

### Column Types
- **IDs**: `BIGINT GENERATED ALWAYS AS IDENTITY` (internal), `UUID` (external)
- **Timestamps**: `TIMESTAMPTZ` (always with timezone)
- **Text**: `TEXT` (avoid `VARCHAR(n)`)
- **JSON**: `JSONB` (for schema flexibility)

## Chunked Asset Storage

Assets containing binary data (audio, video, images, documents) use a chunked storage model that supports streaming writes, append-only immutability for audit trail integrity, and efficient byte-range retrieval.

### Core Requirement: Audit Trail Integrity

Every asset sent to an LLM must be provably the exact bytes that were sent. This means:
- No in-place updates to chunks — chunks are immutable once written
- Clear provenance from draft to finalized asset
- Each chunk has its own timestamp for audit purposes

### Draft and Asset Model

Content is created in two phases:

**Draft Phase (Content Under Construction):**
```
drafts (metadata for in-progress content)
    │
    └── draft_chunks (ordered binary chunks, append-only)
            ├── chunk id=1: bytes 0-262143
            ├── chunk id=2: bytes 262144-524287
            └── ...
```

**Finalized Phase (Immutable Content):**
```
assets (metadata, NO contents column)
    │
    ├── asset_drafts (one-to-one provenance table)
    │       └── draft_id → source draft
    │
    └── asset_chunks (associative table)
            └── chunks (immutable binary data)
```

### Chunk Size

**256KB (262,144 bytes)** per chunk.

| Asset Size | Chunk Count |
|------------|-------------|
| 1 MB | 4 chunks |
| 10 MB | 40 chunks |
| 50 MB | 200 chunks |

### Schema

```sql
-- Draft metadata (content under construction)
CREATE TABLE rev.drafts (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    object_id UUID NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    asset_kind_id SMALLINT NOT NULL REFERENCES rev.asset_kinds (id),
    mime_type TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Draft chunks (append-only during draft phase)
CREATE TABLE rev.draft_chunks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    draft_id BIGINT NOT NULL REFERENCES rev.drafts (id),
    data BYTEA NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT draft_chunk_size CHECK (octet_length(data) <= 262144)
);

-- Finalized chunks (immutable)
CREATE TABLE rev.chunks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    object_id UUID NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    data BYTEA NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chunk_size CHECK (octet_length(data) <= 262144)
);

-- Associative table: assets → chunks (ordered by chunk.id)
CREATE TABLE rev.asset_chunks (
    asset_id BIGINT NOT NULL REFERENCES rev.assets (id),
    chunk_id BIGINT NOT NULL REFERENCES rev.chunks (id),
    PRIMARY KEY (asset_id, chunk_id)
);

-- One-to-one provenance table: asset version → draft
CREATE TABLE rev.asset_drafts (
    asset_id BIGINT NOT NULL REFERENCES rev.assets (id),
    draft_id BIGINT NOT NULL REFERENCES rev.drafts (id),
    PRIMARY KEY (asset_id, draft_id),
    CONSTRAINT uk_asset_drafts_asset_id UNIQUE (asset_id)
);

-- Assets table: drop contents column
ALTER TABLE rev.assets
    DROP COLUMN contents;
```

### Workflow

**1. Create Draft:**
```sql
INSERT INTO rev.drafts (asset_kind_id, mime_type)
VALUES ($1, $2)
RETURNING id, object_id;
```

**2. Append Chunks (Streaming):**
```sql
-- Each INSERT is immediate and immutable
INSERT INTO rev.draft_chunks (draft_id, data)
VALUES ($1, $2)
RETURNING id, created_at;
```

**3. Finalize Draft → Asset:**
Atomically copies draft_chunks to chunks, creates asset, links via asset_chunks.

### Reading Chunks

**Full content:**
```sql
SELECT c.id, c.data
FROM rev.asset_chunks ac
JOIN rev.chunks c ON c.id = ac.chunk_id
WHERE ac.asset_id = $1
ORDER BY c.id;
```

**Byte range (for HTTP Range requests):**
```sql
WITH chunk_positions AS (
    SELECT
        c.id, c.data,
        SUM(octet_length(c.data)) OVER (ORDER BY c.id) - octet_length(c.data) as start_byte,
        SUM(octet_length(c.data)) OVER (ORDER BY c.id) - 1 as end_byte
    FROM rev.asset_chunks ac
    JOIN rev.chunks c ON c.id = ac.chunk_id
    WHERE ac.asset_id = $1
    ORDER BY c.id
)
SELECT id, data, start_byte, end_byte
FROM chunk_positions
WHERE end_byte >= $2 AND start_byte <= $3  -- range bounds
ORDER BY id;
```

### Prohibited Operations

| Operation | Allowed? | Reason |
|-----------|----------|--------|
| `INSERT` into chunks | ✅ | Creates new immutable chunk |
| `UPDATE` on chunks | ❌ | Violates append-only / audit trail |
| `DELETE` on chunks while referenced | ❌ | Breaks asset integrity |

### Versioning Behavior

When an asset is patched (new version):
- New chunks are created (or existing chunks reused if identical)
- New asset row with incremented version
- New asset_chunks links
- Old version remains intact with its chunk links

See `docs/plans/asset-streaming/001-draft-and-asset-chunks.md` for full implementation plan.

## Performance Considerations

### Batch Size
- Optimal batch size: 100-1000 records
- PostgreSQL parameter limit: 65535 (adjust batch size accordingly)

### Indexes
- Create indexes on FK columns
- Add indexes for frequent WHERE/JOIN conditions
- Use partial indexes for filtered queries

### Connection Pooling
```rust
use sqlx::postgres::PgPoolOptions;

let pool = PgPoolOptions::new()
    .max_connections(5)
    .connect(&database_url)
    .await?;
```

## Common Patterns

### Looking Up Shared Dependents
```rust
// 1. Extract object_ids from request
let task_ids: Vec<Uuid> = steps.iter()
    .map(|s| s.task_object_id)
    .collect();

// 2. Batch lookup
let tasks = select_tasks_by_object_ids(&pool, &task_ids).await?;

// 3. Create lookup map
let task_map: HashMap<Uuid, i64> = tasks.iter()
    .map(|t| (t.object_id, t.id))
    .collect();

// 4. Build insert args
let task_internal_ids = steps.iter()
    .map(|s| task_map[&s.task_object_id])
    .collect();
```

### Folding Flat Results
Use `itertools::group_by` to convert JOIN results:

```rust
use itertools::Itertools;

let grouped = flat_rows.into_iter()
    .group_by(|row| row.id);

let models: Vec<_> = grouped.into_iter()
    .map(|(id, group)| fold_group(id, group))
    .collect();
```

## SQLx Offline Mode

Prepare query metadata for CI/Docker builds:

```bash
# Generate .sqlx/ directory (preferred: `dapple sqlx prepare`, which wraps this).
# `-- --all-targets` makes the cache cover test-target inline `sqlx::query!` too,
# so the offline CI build of the tests doesn't fail on a missing query.
cargo sqlx prepare --workspace -- --all-targets

# Enable offline mode
export SQLX_OFFLINE=true
cargo build
```

Commit `.sqlx/` directory to git for offline verification.

## Contributing

When adding new queries:

1. Create `.sqlc` source in `assets/sqlc/{principal}/` — use `:compose()` for shared CTEs, `:bind()` for parameters
2. Run `cargo sqlc compose --source assets/sqlc/ --target assets/.sql/` to generate output
3. Define model types in `src/model/{principal}.rs`
4. Implement query function in `src/query/{principal}.rs` — pass `query_file_as!` params in **alphabetical order** of `:bind()` names, referencing `"assets/.sql/..."` paths
5. Run `dapple sqlx prepare` (raw: `cargo sqlx prepare --workspace -- --all-targets`)
6. Add integration test in `dapple-prompt-api/tests/`

**Never edit files in `assets/.sql/` directly** — they are generated by sql-composer and will be overwritten.

See [CLAUDE.md](../../CLAUDE.md) for comprehensive guidelines.
